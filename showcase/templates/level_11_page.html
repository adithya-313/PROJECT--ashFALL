How a run works

A run turns a few settings into a complete, repeatable world. Configuration files hold every number with a label saying where it came from. Optional layer files change named settings for one run. The world is built from a seed, a calendar plan is drawn, and a calendar runner moves money through three bank ledgers minute by minute. The run writes an events file, a manifest that fingerprints it, and a world card that describes it. Live mode can replay the same events to a receiver one by one.

$pipeline_svg
Plan streamfestivals, rhythms, outages, failure rates
Payment streamwho pays whom, when and how much
Device streamphone changes, reinstalls, OS update waves
Episode streamweddings, chit funds, bills for relatives

One seed is split into four independent random streams. A new feature draws from its own stream, so the numbers older features produce never shift. That is what keeps the golden fingerprints valid as the engine grows.

Stress tests

A stress test takes a real event and deliberately exaggerates it, like a fire drill. Each one is a layer file in scenarios/stress/ that names the real event and the size of the exaggeration, and every run that uses one is labelled as a stress test on its world card.

How it is tested

Three layers of protection run on every change. Golden fingerprints catch any change to what a world contains. The test suite checks behaviour, including statistical properties and failure paths. Worked examples inside the code's documentation are executed as tests, so the documentation cannot drift from the code.
